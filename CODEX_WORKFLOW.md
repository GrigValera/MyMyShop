# CODEX_WORKFLOW.md

Единый стандарт работы Codex для всех репозиториев портфеля.

Стандарт применяется к каждому ticket. Реализация должна соответствовать утверждённому Master Development Plan и согласованному scope ticket. При противоречии или отсутствии необходимых требований Codex останавливает работу и запрашивает уточнение.

## Основные правила

1. Один ticket = одна отдельная branch.
2. До любых изменений Codex проверяет Git status, текущую branch и HEAD. Рабочее дерево должно быть чистым.
3. Codex работает только над явно подтверждённым пользователем ticket.
4. Массовые refactor и dependency upgrades вне scope ticket запрещены.
5. Любое необходимое расширение scope требует остановки и согласования до реализации.
6. После каждого ticket приложение должно оставаться работоспособным.
7. Все изменения должны быть откатываемыми через Git. Миграции и изменения внешнего состояния требуют описанного и проверяемого плана восстановления.
8. Security fixes нельзя откатывать к уязвимому состоянию.
9. README должен соответствовать фактической реализации.
10. Codex не начинает следующий ticket автоматически. Требуется явное подтверждение пользователя.

## PROJECT LANGUAGE POLICY

Основной язык описательной части MyMyShop — русский. На русском пишутся связный текст PR body (PR description), итоговые отчёты по ticket, review summary, инструкции для reviewer и пользователя, пояснения в README и ROADMAP, UX-аудитах и архитектурной документации, авторские поясняющие комментарии в коде, тестах и стилях, а также заметки для разработчиков внутри репозитория. Правило действует для новых и изменяемых текстов; историю старых PR и commits ради языка не переписывают.

Английский допустим для технических идентификаторов, имён файлов, компонентов, сервисов, функций и классов, названий библиотек, фреймворков и технологий, маршрутов, CLI-команд и их вывода, имён веток и ticket ID, переменных окружения, API-имён, технических названий и идентификаторов тестов, статусов Git/GitHub, обязательного стороннего текста, лицензий и заголовков, сгенерированных комментариев и директив инструментов. Технические идентификаторы не переводятся ради формального соблюдения правила. Английские технические термины допустимы внутри русского пояснения.

Заголовок PR может оставаться на английском в conventional-commit style, например `fix(shop): ...`. Связное пояснение в PR body пишется на русском.

## UX / PRODUCT BENCHMARK GATE

Перед реализацией нового или существенно изменяемого пользовательского потока (навигация, Account, каталог, PDP, корзина, checkout, платежи, доставка, заказы, формы, mobile shell) Codex сначала фиксирует короткое UX decision summary. Оно содержит: user jobs; 1–2 релевантных источника UX research и 2–4 примера зрелых продуктов, когда доступны; повторяющиеся patterns; выбранный и отклонённые варианты с причиной; связь с текущей product IA и domain contract; поведение desktop/tablet/mobile, keyboard, RU/EN и light/dark; путь расширения будущих возможностей. Изучаются принципы, а не копируются визуальный стиль и тексты бренда.

Порядок для major UX: **benchmark → user jobs → product IA → domain contract → UX decision → implementation → automated QA → human product review**. Summary показывается пользователю до изменений runtime UI и сохраняется в ticket documentation или соответствующем decision/audit документе. Если внешние источники недоступны и решение действительно требует исследования, нельзя выдавать предположение за benchmark: работа останавливается перед major IA redesign, ограничение сообщается пользователю. Мелкие исправления существующего контракта не требуют нового полного benchmark, но опираются на уже зафиксированное решение.

## DOMAIN-WIDE CONSISTENCY CHECK

Ticket реализует domain capability, а не изолированный компонент. Перед изменением Codex перечисляет затронутые поверхности и проверяет их согласованность: например, Orders связывают кабинет, checkout success, детали, доставку, статусы, уведомления, tests и docs; Cart связывает карточки, PDP, drawer, страницу корзины и checkout. В рамках ticket синхронизируются все поверхности, необходимые для правдивого текущего поведения. Независимые улучшения других доменов выносятся в отдельный backlog/ticket; mass refactor не следует из аудита.

Полная product IA может предшествовать бизнес-возможностям. Нереализованные разделы получают честное empty/coming-soon состояние без вымышленных заказов, платежей, адресов и статусов. Demo mechanics раскрываются коротко в интерфейсе и подробно в README/docs. Customer-facing текст объясняет задачу и доступное действие, а не устройство services/adapters.

## RESPONSIVE / PRODUCT REVIEW CHECK

Responsive quality входит в Definition of Done runtime UI ticket. Проверяются 320, 390, 400, 480, 768, 769, 1024, 1280 и 1440 px либо обоснованный subset, обе локали и темы, keyboard/focus, error/empty states, столкновения fixed controls и отсутствие horizontal overflow. Одна product IA должна иметь осмысленную композицию на mobile, tablet и desktop. До передачи на Manual QA Codex просматривает целый экран и ключевые journeys как reviewer: понятны ли местоположение, доступные функции, главное действие и следующий шаг без архитектурных документов. Проверка визуальной иерархии включает typography, spacing, alignment, action/field priority и icon geometry.

## Git workflow

### Перед изменениями

Codex выполняет и показывает результаты:

- `git status --short --branch`
- `git branch --show-current`
- `git rev-parse HEAD`

Условия начала работы:

- Рабочее дерево чистое, включая отсутствие неучтённых файлов.
- Нет незавершённого merge, rebase или cherry-pick.
- HEAD находится на именованной branch.
- Определена согласованная базовая branch.
- Для ticket создана или выбрана отдельная branch.
- Зафиксирован исходный HEAD для сравнения и возможного отката.

Если рабочее дерево не чистое, Codex останавливается. Нельзя автоматически удалять изменения, выполнять reset, stash или commit для очистки дерева.

Рекомендуемое имя branch: `ticket/<ticket-id>-<short-description>`.

### Во время реализации

- Все изменения относятся к текущему ticket.
- Несвязанные проблемы фиксируются в отчёте и не исправляются без согласования.
- Если без расширения scope продолжение невозможно, работа останавливается.
- Проверки выполняются по фактической конфигурации репозитория.
- README обновляется, если ticket меняет описанное поведение, настройку, команды или ограничения приложения.

## Automated checks и отчёт

### Applicability проверок

Перед завершением ticket Codex обязан определить его тип по итоговому diff, указать обоснование и применимость проверок.

#### Runtime-impacting

К этому типу относятся изменения кода, UI, CSS, HTML, зависимостей, build/runtime config, API, storage, routing, manifest и другого поведения приложения.

Любое изменение, способное повлиять на build, runtime, deployment, security или пользовательское поведение, считается Runtime-impacting.

Для таких tickets обязателен полный процесс:

automated checks
→ production build
→ production preview
→ manual QA
→ MANUAL QA PASSED
→ commit.

#### Non-runtime

К этому типу могут относиться изменения:

- README;
- CODEX_WORKFLOW.md;
- ROADMAP;
- документации;
- GitHub profile content;
- только комментариев в коде.

Перечень не означает автоматического освобождения от проверок. Классификация определяется фактическим влиянием изменений. Например, документация или комментарии, влияющие на сборку, генерацию, security или deployment, относятся к Runtime-impacting.

Для Non-runtime tickets production build, production preview, E2E, visual regression и runtime testing могут иметь статус `NOT APPLICABLE`, если Codex явно объяснил неприменимость каждой проверки.

Применимые проверки содержания и файлов выполняются, включая настроенные lint, форматирование и проверки ссылок, если они относятся к изменениям.

Процесс для Non-runtime tickets:

определение applicability
→ применимые automated checks
→ ручная проверка итогового diff и содержания пользователем
→ MANUAL REVIEW PASSED
→ commit.

Нельзя использовать классификацию Non-runtime для обхода проверок. Если отсутствие влияния нельзя обосновать, ticket считается Runtime-impacting. Если ticket содержит оба типа изменений, применяется процесс Runtime-impacting.

### Проверки и итоговый отчёт

После реализации Codex выполняет применимые проверки и показывает:

1. Тип ticket и обоснование классификации.
2. Diff summary: суть и объём изменений.
3. Полный список изменённых и добавленных файлов.
4. Добавленные или изменённые tests; если их нет — объяснение.
5. Результаты tests.
6. Результаты lint.
7. Результаты production build.
8. Результаты E2E и visual checks, если они настроены, либо обоснование неприменимости.
9. Известные риски и ограничения.

Для каждой проверки указываются команда, если она выполнялась, и результат:

- `PASSED` — проверка выполнена успешно.
- `FAILED` — проверка выполнена с ошибками.
- `NOT CONFIGURED` — применимая проверка не настроена.
- `BLOCKED` — применимая проверка не может быть выполнена; указан блокер.
- `NOT APPLICABLE` — проверка неприменима к итоговым изменениям; приведено явное обоснование.

Невыполненная проверка не считается пройденной. `NOT CONFIGURED` и `BLOCKED` нельзя заменять на `NOT APPLICABLE` ради обхода проверок.

Ошибки обязательных проверок блокируют завершение ticket. Отсутствующие проверки явно отмечаются; необходимое расширение инфраструктуры согласовывается отдельно.

## Production preview

### Runtime-impacting tickets

После automated checks Codex обязан собрать и запустить production preview текущей реализации.

- Preview должен обслуживать production build, а не development server.
- Используется предусмотренный репозиторием способ запуска.
- Codex проверяет доступность preview и сообщает URL, команду запуска и необходимые инструкции.
- Если сборка или запуск невозможны, Codex сообщает блокер. Manual QA Gate остаётся закрытым.
- Если production preview не предусмотрен, способ проверки согласовывается с пользователем до дальнейшего продвижения.
- После исправлений production build пересобирается, а preview обновляется.

Пользователь вручную тестирует именно этот production build.

### Non-runtime tickets

Production build и production preview могут иметь статус `NOT APPLICABLE` с отдельным обоснованием неприменимости.

В этом случае Codex предоставляет пользователю итоговый diff и содержание изменений для ручной проверки. Отсутствие preview не отменяет обязательного MANUAL REVIEW PASSED.

## Manual QA Gate

### Runtime-impacting tickets

До ручной проверки Codex подготавливает checklist для текущего ticket:

- [ ] Выполнены acceptance criteria ticket.
- [ ] Основной пользовательский сценарий работает.
- [ ] Проверены затронутые соседние сценарии.
- [ ] Проверены применимые ошибочные и граничные состояния.
- [ ] Для UI проверены затронутые экраны, состояния и размеры viewport.
- [ ] Нет новых ошибок, мешающих работе приложения.
- [ ] README соответствует реализации.

Каждый пункт конкретизируется: действия, тестовые данные и ожидаемый результат. Неприменимые пункты отмечаются с объяснением. Используются только безопасные demo-данные.

Решение принимает пользователь:

#### MANUAL QA FAIL

- Текущий ticket остаётся открытым.
- Codex исправляет выявленные проблемы в текущей branch.
- Если исправление выходит за scope, Codex останавливается для согласования.
- Automated checks повторяются.
- Production build пересобирается, production preview обновляется.
- Отчёт и manual QA checklist актуализируются.
- Новый build снова передаётся пользователю на ручную проверку.
- Commit запрещён до MANUAL QA PASSED.

#### MANUAL QA PASSED

- Только явное подтверждение пользователя открывает возможность commit.
- Подтверждение относится к конкретному проверенному build и набору изменений.
- Любые последующие изменения требуют повторных применимых проверок и нового ручного подтверждения по типу итогового ticket.
- Молчание пользователя или успешные automated checks не заменяют ручное подтверждение.

### Non-runtime tickets

Вместо ручного тестирования production build пользователь проверяет итоговый diff и содержание изменений.

Codex подготавливает manual review checklist:

- [ ] Изменения соответствуют scope и acceptance criteria ticket.
- [ ] Итоговый diff не содержит посторонних изменений.
- [ ] Содержание корректно, полно и внутренне согласовано.
- [ ] Документация соответствует фактической реализации.
- [ ] Применимые ссылки, примеры и команды проверены.
- [ ] Классификация Non-runtime и статусы NOT APPLICABLE обоснованы.

При отрицательном результате ручной проверки:

- Текущий ticket остаётся открытым.
- Codex исправляет замечания в текущей branch.
- Если исправление выходит за scope, Codex останавливается для согласования.
- Классификация и applicability пересматриваются по новому diff.
- Применимые automated checks повторяются.
- Итоговый diff, отчёт и checklist снова передаются пользователю.

Commit допускается только после явного MANUAL REVIEW PASSED.

Подтверждение относится к конкретному итоговому diff и содержанию. Любые последующие изменения требуют повторных применимых проверок и нового ручного подтверждения. Если ticket становится Runtime-impacting, требуется полный процесс с MANUAL QA PASSED.

## Commit / Push / Merge policy

### LANGUAGE CHECK — обязательный gate перед PR

Перед созданием каждого PR Codex проверяет итоговый PR body и diff:

- [ ] Связный текст PR body написан на русском; заголовок может быть conventional-commit style на английском.
- [ ] Новые авторские поясняющие комментарии в коде, тестах и стилях написаны на русском.
- [ ] Новые пояснения в README, ROADMAP, docs и аудитах написаны на русском.
- [ ] Инструкции для reviewer и пользователя написаны на русском.
- [ ] В изменённых материалах нет случайных поясняющих абзацев на английском.
- [ ] Технические идентификаторы и согласованные исключения не переведены без причины.

Результат LANGUAGE CHECK включается в отчёт перед PR. При невыполненном пункте PR не создаётся до исправления или документированного обоснования исключения.

### Commit

- Для Runtime-impacting ticket commit допускается только после явного MANUAL QA PASSED.
- Для Non-runtime ticket commit допускается только после явного MANUAL REVIEW PASSED.
- Ручное подтверждение должно относиться к итоговому набору изменений.
- Перед commit Codex проверяет итоговый diff и состав staged-файлов.
- Commit содержит только изменения текущего ticket.
- В сообщении commit указывается ticket ID и суть изменения.
- После commit Codex сообщает commit hash и Git status.
- Commit сам по себе не разрешает push, merge или следующий ticket.

### Push

- Push выполняется только после отдельного явного разрешения пользователя.
- Разрешение на commit не является разрешением на push.
- Разрешение относится к согласованной branch и набору commits.
- Force push требует отдельного явного согласования.

### Merge

- Merge выполняется только после отдельного явного разрешения пользователя.
- Разрешение на push не является разрешением на merge.
- Перед merge проверяются актуальные обязательные checks и целевая branch.
- Если разрешение конфликтов меняет проверенную реализацию, проверки и Manual QA Gate повторяются.

### Deployment

Deployment проверяется отдельно от Git merge.

- Успешный merge не подтверждает успешный deployment.
- Deployment требует явного разрешения либо ранее согласованной автоматической политики.
- Если push или merge запускает автоматический deployment, Codex сообщает об этом до действия.
- Проверяются результат deployment, опубликованная версия, доступность приложения и основные smoke-сценарии.
- Результаты deployment сообщаются отдельно от результатов merge.

## Definition of Done

Ticket завершён, когда выполнены все общие условия и условия для его типа.

### Общие условия

- [ ] Реализован согласованный scope и acceptance criteria.
- [ ] Нет несогласованных изменений вне scope.
- [ ] Определён и обоснован тип ticket по итоговому diff.
- [ ] Applicability проверок явно указана; каждый NOT APPLICABLE обоснован.
- [ ] Приложение остаётся работоспособным.
- [ ] Tests добавлены или обновлены по необходимости.
- [ ] Обязательные применимые automated checks пройдены.
- [ ] README соответствует фактической реализации.
- [ ] Предоставлены diff summary, список файлов, результаты проверок и известные риски.
- [ ] Описан безопасный способ rollback.
- [ ] Commit создан после соответствующего ручного подтверждения; рабочее дерево чистое.

### Runtime-impacting

- [ ] Production build успешно собран.
- [ ] Настроенные E2E и visual checks пройдены.
- [ ] Production preview запущен и доступен пользователю.
- [ ] Пользователю предоставлен manual QA checklist.
- [ ] Пользователь проверил итоговый production build.
- [ ] Получено явное MANUAL QA PASSED для итоговой реализации.

### Non-runtime

- [ ] Отсутствие влияния на build, runtime, deployment, security и пользовательское поведение обосновано.
- [ ] Для неприменимых production build, preview, E2E, visual regression и runtime testing указан NOT APPLICABLE с объяснением.
- [ ] Пользователю предоставлены итоговый diff и manual review checklist.
- [ ] Пользователь проверил итоговый diff и содержание изменений.
- [ ] Получено явное MANUAL REVIEW PASSED.

Push, merge и deployment имеют отдельные статусы и разрешения. Они не выполняются автоматически при достижении Definition of Done.

После завершения ticket Codex останавливается и ожидает явного подтверждения пользователя перед следующим ticket.

## Rollback policy

- Изменения должны иметь понятный путь отката через Git.
- Для опубликованных commits предпочтителен `git revert`, сохраняющий историю.
- Нельзя уничтожать пользовательские изменения или переписывать общую историю без отдельного разрешения.
- До rollback оцениваются влияние на данные, миграции, конфигурацию и совместимость.
- Git rollback сам по себе не восстанавливает базы данных или внешние сервисы. Для них требуется отдельная процедура восстановления.
- Необратимые изменения без согласованного плана восстановления не допускаются.
- Rollback не должен возвращать известную уязвимость. Используется безопасный revert или корректирующее исправление.
- После rollback повторяются применимые проверки, production build и ручная проверка.
- Если rollback затрагивает deployment, его результат проверяется отдельно.

## Security policy

- В demo-проектах запрещены реальные credentials.
- Используются placeholders, mocks или предназначенные для демонстрации тестовые данные.
- Secrets нельзя помещать в код, commits, README, fixtures, логи или клиентский bundle.
- Примеры конфигурации содержат только безопасные значения.
- Найденные credentials не копируются в отчёт. Codex сообщает о находке без раскрытия значения.
- Необходимые отзыв или ротация credentials согласовываются с пользователем.
- Security fixes нельзя откатывать к уязвимому состоянию.
- Нельзя отключать защитные проверки ради прохождения tests или build.
- Security-проблемы вне scope сообщаются пользователю. Расширение ticket согласовывается до изменений.
