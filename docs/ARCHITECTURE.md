# Архитектура MyMyShop — SHOP-ARCH-01

Исходная архитектурная фиксация сделана на коммите `8232dd5558aad6e6932960926e682bc1a2839903` (2026-10-08); разделы CURRENT обновлены для SHOP-UX-COMMERCE-01. **CURRENT** — подтверждено кодом; **PLANNED** — запланировано, но не реализовано; **PROPOSED** — архитектурное предложение, требующее отдельного решения; **OPTIONAL** — необязательная возможность без утверждённого решения. Упоминание домена или внешней системы не означает наличие развёрнутого backend, поставщика или интеграции.

Сейчас MyMyShop — демонстрационный магазин на React и Fastify backend с app-owned session. Публичные страницы каталога и корзины работают без API, вход в демо-аккаунт требует backend. Сервер не обслуживает commerce. Публичный demo должен честно показывать ограничения локальных данных, заказов и оформления.

**SHOP-BACKEND-FOUNDATION-01 — CURRENT:** [стратегия интеграций](INTEGRATION_STRATEGY.md) закрепляет самостоятельный каталог без credentials; вход в демо-аккаунт использует данные, показанные в UI. Backend отделён от frontend: `server/` содержит Fastify, config, SQLite, миграции, identity verifier, session и profile services. `Order` принадлежит MyMyShop, а не поставщику, но Order и test integrations ещё отсутствуют.

## Слои и границы

**CURRENT:** представление находится в `src/pages` и `src/shared`; состояние пользовательских функций и прикладная логика сосредоточены преимущественно в Redux и `src/features`. `sessionService → httpSessionAdapter` и `accountService → httpAccountAdapter` подключены к app-owned session и профилю; корзина хранится в `localStorage`, каталог дополнительно использует RTK Query для DummyJSON. Разделение каталога неполное: `ProductsPage` и `ProductDetailsPage` выбирают `?source=api` и непосредственно используют данные источника. Бизнес-системы не подключены.

**PLANNED — целевая граница:**

```mermaid
flowchart LR
  C[Покупатель] --> W[Веб-приложение MyMyShop]
  W --> A[MyMyShop Backend / Application API]
  A --> D[Доменная и прикладная граница]
  D --> I[Адаптер интеграции]
  I --> E[Внешняя бизнес-система]
```

Интерфейс должен зависеть от контрактов функций и доменов, а не от конкретного источника данных, SDK поставщика, DTO внешней системы или demo-реализации адаптера. **PLANNED:** MyMyShop Backend / Application API отвечает за учётные данные, достоверные цены, заказы, платёжные статусы, права доступа и внешние интеграции. **PROPOSED:** явные сервисные и доменные границы не требуют отдельных процессов: первоначальный backend **может** быть модульным монолитом. Для микросервисов нет принятого решения или текущей потребности. Исключение для браузера возможно в виде защищённого платёжного интерфейса или перенаправления поставщика; намерением платежа, связью с заказом и проверкой статуса всё равно управляет backend.

## Статический demo и приложение с backend

**CURRENT:** локальный снимок каталога, дополнительный публичный режим DummyJSON и Redux-корзина работают без backend. Демо-вход проверяет email и пароль на сервере и использует server-side cookie session с постоянным demo actor, поэтому функциональному публичному demo нужны HTTPS, API, постоянная SQLite, SPA fallback и abuse protection. Публикация не подтверждена. Внешней identity integration, оформления заказа, Order, Payment и исполнения заказа нет. `/checkout` — предварительный просмотр; корзина сохраняется.

**PLANNED:** production identity provider вместо проверки demo credentials, расширение серверного профиля/аватара, бизнес-функции адресов, реальные Orders и Order Details, Shipment Tracking, Checkout, Payments, Refunds и Support через MyMyShop Backend / Application API и серверные адаптеры интеграций. Демонстрационные Order History и Order Details уже работают на фиксированных снимках. **PROPOSED:** явные сервисные/доменные контракты и преобразование DTO в модели интерфейса; будущий provider заменяет слой проверки личности, сохраняя UI и app-owned session architecture. Будущий ticket отзывов должен проследить путь `данные источника → преобразование/нормализация → модель frontend/домена → представление на PDP`. Контракты, маршруты и схемы утверждаются в следующих tickets.

## Принципы и открытые решения

**Product IA / domain consistency:** до major user-facing реализации фиксируется UX decision summary по [workflow](../CODEX_WORKFLOW.md); бизнес-возможность согласуется во всех затронутых поверхностях, а не только в одном компоненте. Полная структура кабинета может существовать раньше бизнес-возможностей: Orders теперь показывает фиксированные demo данные, Addresses/Reviews/Settings — честные placeholder-состояния. Findings по другим экранам и их отдельные зависимости описаны в [UX/Product audit](UX_PRODUCT_AUDIT.md) и ROADMAP; аудит не добавляет runtime-функции.

- **CURRENT — подтверждённые факты:** [архитектура frontend](FRONTEND_ARCHITECTURE.md) и [среды поставки](DELIVERY_AND_ENVIRONMENTS.md).
- **PLANNED — правило:** UI не интегрируется напрямую с CRM, ERP, WMS, backend API PSP и перевозчика. Изменяемое состояние браузера не является источником истины для чувствительных операций.
- **PROPOSED — правило:** при подключении backend использовать явные контракты функций и преобразование DTO; сохранять границы ответственности и в одном развёрнутом backend.
- **Открыто:** размещение backend, поставщики, commerce API, транспорт настоящей сессии, согласование корзины, способ оплаты, статусы заказа, сроки хранения данных и операционные цели. Stack foundation — Fastify/JavaScript/SQLite; дальнейшие решения принимаются в отдельных tickets. Граница backend и владение `Order` определены в [стратегии](INTEGRATION_STRATEGY.md).
